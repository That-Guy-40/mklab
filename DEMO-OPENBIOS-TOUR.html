Firmware is the code that runs before the operating system — and when it's wrong, the machine won't boot and there's no OS to SSH into to fix it. This is a family of labs that make firmware inspectable and editable: a Forth prompt you can type at while the machine sits there, pre-OS, and a toolkit that reads and rewrites the binary formats a boot chain is made of. Everything runs in QEMU, as a normal user, no hardware required.

a 60-second glossary

Six terms, then we're off

Tap any term for the plain-English version.

bzImage— a compiled, compressed Linux kernel: the file a bootloader loads. initrd— a tiny first root filesystem (a cpio archive) the kernel mounts before the real disk. UKI— Unified Kernel Image: one signed .efi file with the kernel, initrd, and command line glued on as sections. the ok prompt— the interactive Forth language built into Open Firmware. You type words; it runs them now. device tree— a binary map of a machine's hardware firmware hands the kernel. Everywhere in switches & routers. foreign oracle— an independent tool (dtc, objdump, cpio) used to check the firmware's answer. The firmware is never its own judge.
the centerpiece

Rescue a machine that won't boot — no USB stick, no chroot

A boot artifact is deliberately broken so the machine hangs, then repaired in place by the firmware itself, pre-OS. The kind of fix you'd normally do by pulling the disk, booting a rescue USB, and chroot-ing in.

one command 
$ examples/openbios-the-rival-that-shipped/showcase-rescue.sh all

Four independent acts, each on a different kind of boot artifact. The negative control is the point: each act first boots the un-repaired artifact and shows it genuinely failing, so when the fixed one comes up you know the edit is what rescued it.

act · initrd

No initrd

Boot with no initrd → kernel can't mount root → supply the good one on the boot line.

act · config

Bad config in the initrd

Firmware edits a file inside the initramfs in place, same length, archive stays valid.

act · cmdline

UKI missing a flag

Grow the UKI's .cmdline section to add the rescue flag; it boots under real UEFI.

act · bzImage

Kernel's live command line

Follow the bzImage's cmd_line_ptr in RAM and rewrite the line; an outside decoder confirms it.

PASS ✓ — three in-place editors, each turned on its native artifact type, each rescuing a broken boot with no USB stick and no chroot. Verified end-to-end on 2026-10-06: every act's broken artifact failed first (VFS: Unable to mount root fs / RESCUE-FAIL), then the repaired one reached its shell.

Run a single act too: showcase-rescue.sh bzimage, … config, … cmdline, … initrd.

the toolkit

Understand any boot artifact — graded against an outside tool

Before you can safely edit a boot artifact you have to read it correctly. Each reader is checked field-for-field against the standard third-party tool, on four CPU architectures at once — because byte order is exactly the thing that's right on one CPU and silently wrong on another.

smoke-openbios.sh — four readers 
# a bzImage's boot header, a UKI's sections, an initrd's members, the live device tree
$ examples/openbios-the-rival-that-shipped/smoke-openbios.sh bootparams
$ examples/openbios-the-rival-that-shipped/smoke-openbios.sh pe
$ examples/openbios-the-rival-that-shipped/smoke-openbios.sh cpio
$ examples/openbios-the-rival-that-shipped/smoke-openbios.sh fdt
PASS: the firmware's LIVE device tree, flattened and accepted by dtc itself,
      on all four arches; fdtdump's node and property counts equal the firmware's.

The fdt one lands with network engineers: it's the same flattened device tree that describes the hardware inside switches, routers and SBCs — here the firmware generates it live and a real dtc signs off on it.

why you can trust it

The part worth lingering on

This is the difference between a demo and a result. The testing discipline is deliberately paranoid.

Foreign oracle

Every claim is checked by an independent tool — dtc, objdump, cpio, tpm2_eventlog. "The firmware printed the right answer" is never the test.

Controls that bite

A checker that only ever passes checks nothing. Each test also breaks the subject and confirms the assertion fails — the un-repaired artifact is shown failing first, every time.

UNKNOWN ≠ PASS

A missing prerequisite SKIPs by name (exit 77). "I couldn't check this" never silently becomes "this is fine."

Outcome, not mechanism

The symbol-poke demo doesn't check "the firmware found the symbol table" — it pokes a function and checks the running program emits the poked value.

found while building this tour

Verifying the rescue showcase surfaced a real bug: the bzImage fixture capture moved a scratch file from /tmp to the workdir with os.replace(), which throws EXDEV when (as on most laptops) /tmp is a separate filesystem. The run failed honestly with the traceback instead of silently skipping.

It's fixed now — copy beside the destination, then atomically rename — and the fix was watched working across the real device boundary before this sentence was written. That's the ethos in miniature: run it, don't reason about it; fix the thing that lies before the thing that merely breaks.
